## 2. Audit: is the app actually reading from Supabase, or from something else?

Go through every data-driven feature and confirm each one reads from the **live Supabase database** as its primary source — not a hardcoded array, a local mock, or a same-server in-memory default that's silently preferred over the real data:

- **Products** (`src/components/brand/Products.tsx`) — this file has a `FALLBACK` seed array. Confirm precisely when it's used: it must trigger **only** when the Supabase request itself fails/errors (network failure, misconfigured keys, etc.) — never when the request succeeds but simply returns zero active products. Those are two different situations ("can't reach the data" vs. "reached it, there's nothing there right now") and must not be handled the same way. If the current code can't tell them apart, fix that distinction specifically — don't remove the fallback outright, since a genuine connection-failure fallback is reasonable defensive UX; just make sure it isn't masking "database is actually fine but query is subtly wrong."
- **FAQs, Blog posts, Hero carousel, Gallery, Media Center assets, Homepage sections (Our Story/Mission/Vision), Product categories** — grep each corresponding component for any hardcoded array of seed-looking data sitting alongside (or instead of) a real `supabase.from(...)` call. Where one exists, apply the same test as above: legitimate error-state fallback only, never a silent default that masks whether the live connection is actually working.
- **Partners** (`PartnerContext.tsx`, `PartnerSetup.tsx`, admin `PartnersPage.tsx`) — these should have no fallback data at all; a partner site with no real database connection should show a clear error/loading-failed state, not any kind of placeholder partner content, since showing fake partner data to a real visitor would be actively misleading.
- **Distributor dashboard, commissions, wallet, compensation-plan figures** — confirm none of these ever fall back to placeholder/demo numbers under any circumstances. A failed connection here must show an explicit error, never zero-filled or fake-looking data that could be mistaken for real figures.
- Server-side (`server.ts`): confirm every route wrapped in `requireDb` genuinely fails closed (returns its configured 503 "Database not configured" response) when `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` are missing, rather than silently falling back to any in-memory/local data path.

Produce a short written list of every file where a fallback/hardcoded data path exists, what triggers it today, and whether that trigger condition is correct per the rule above. Fix only the ones that are wrong — don't remove legitimate error-state fallbacks.
