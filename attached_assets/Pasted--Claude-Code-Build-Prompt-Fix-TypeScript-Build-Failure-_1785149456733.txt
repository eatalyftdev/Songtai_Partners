## 1. Read the log correctly — "Emit skipped" is not the error

The Vercel build failed with:
```
Error: src/routes/partners.ts: Emit skipped
```

This is `tsc --build`'s summary line, printed for a file once it has one or more real type errors and the composite build has `noEmitOnError` in effect (the default for project-reference builds). **The actual diagnostic (file:line:column, error code, and message) is printed immediately above this line** — the pasted log was cut off right at this line, so the real cause hasn't been seen yet. Do not attempt a fix based on "Emit skipped" alone.

Run `pnpm run build` (or `tsc --build --verbose`) from the root to see the full dependency-order build output, not just the `api-server` package in isolation.

## 3. Likely causes for this specific setup (check in this order)

Given the stack (Drizzle ORM + a shared `@workspace/db` schema package + a shared `@workspace/api-zod` validation package + Express route file), the most common causes of a route file failing to emit are:

1. **Schema/type drift between `@workspace/db` and the route file** — if a Drizzle table/column was recently added, renamed, or retyped in `@workspace/db` (e.g. matching the `partners` table's recent additions: `deployment_mode`, `standalone_url`, `setup_completed_at`, `display_name`, `pending_contact_name/phone`, `domain_status`, etc.) but `src/routes/partners.ts` wasn't updated to match, or vice versa — TypeScript will fail to compile the mismatch. Compare the current Drizzle schema definition for `partners` against what the route file actually reads/writes.
2. **Zod schema mismatch in `@workspace/api-zod`** — if request/response validation schemas for the partners routes were defined separately from the Drizzle types and one was updated without the other, a type mismatch between "what Zod expects" and "what Drizzle returns" is a common source of exactly this kind of emit failure.
3. **A stale/missing type export** — if `@workspace/db` or `@workspace/api-zod` recently added a new exported type/enum (e.g. for `deployment_mode: 'shared_path' | 'standalone'`) but didn't rebuild its own `dist`/declaration output before `api-server` referenced it, the project-reference build can fail on an import that TypeScript can't resolve or that resolves to a stale shape. Run a full clean build from the root (`pnpm run build` at the repo root, not just the affected package) to rule this out before debugging the route file itself.
4. **An actually-wrong line in the route file** — once the real error message is visible, if it's a straightforward local mistake (wrong property name, wrong argument type, missing await, etc.), fix it directly and precisely — don't broaden the fix beyond the specific reported line/error.
