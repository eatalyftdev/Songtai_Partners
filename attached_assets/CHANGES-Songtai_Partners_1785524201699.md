All verified by actually running the real build in this monorepo (`pnpm run typecheck`, `pnpm run build`) — not assumed from reading code.

## Bugs found and fixed

| File | Bug | Fix |
|---|---|---|
| `lib/api-zod/src/index.ts` | Duplicate blanket `export *` lines caused a real export-name collision (`RequestUploadUrlBody`/`RequestUploadUrlResponse` existed as both a Zod const and a TS interface) — this is what was actually behind the original `src/routes/partners.ts: Emit skipped` Vercel build failure. **Note:** this file gets regenerated by `pnpm run codegen` and reverted the fix once during this session — spot-check it after any future codegen run. | Removed the two redundant lines; confirmed `storage.ts` only ever needed the Zod runtime versions, not the TS types, so nothing else broke. |
| `artifacts/songtai-partners/src/pages/partner/PartnerSite.tsx` | 28 TypeScript errors — `ease: [0.22, 1, 0.36, 1]` cubic-bezier arrays in untyped `variants` objects were inferred as generic `number[]`, incompatible with Framer Motion's expected type. | Explicitly typed `fadeUp`/`fadeIn`/`stagger`/`cardItem` as `Variants` (imported from `framer-motion`). |
| `src/pages/admin/FaqManage.tsx` | `category: string \| null` sent where the API expects `string \| undefined`. | Changed to `form.category \|\| undefined`. |
| `src/pages/admin/ProductsList.tsx` | `product.stock` used directly where it's typed as possibly `undefined`. | Guarded with `(product.stock ?? 0)`. |
| **`artifacts/api-server/src/lib/supabaseStorage.ts`** | **The actual root cause of "uploads fail for both product images and partner images."** The signed-upload-URL request hit `/storage/v1/object/sign/upload/...` — Supabase's real API path is `/storage/v1/object/upload/sign/...` (segments swapped). Every upload always 404'd. Both `ProductsList.tsx` and `PartnerEdit.tsx` go through this exact same function via `@workspace/object-storage-web`'s `useUpload` hook, so this one fix resolves both symptoms. | Swapped the path segments to match Supabase's real API. |

`mockup-sandbox` (a separate, unrelated demo package) fails locally on a missing `PORT` env var — pre-existing, not touched, almost certainly irrelevant to how Railway actually deploys this (it deploys `api-server`/`songtai-partners` specifically, not the whole monorepo).

## Custom domain resolution (the coachnelson.site work)

- **Schema**: added `customDomain` (unique) and `domainStatus` (`none`/`pending_verification`/`verified`/`failed`, default `none`) to the `partners` Drizzle table.
- **Source of truth updated properly**: added the new fields and a `GET /partners/by-domain?hostname=...` path to `lib/api-spec/openapi.yaml` (not hand-edited into the generated Zod files, which would just get overwritten), then regenerated via `pnpm run codegen`.
- **Server**: new `GET /partners/by-domain` route (must be registered before `/partners/:slug` so `by-domain` is never parsed as a literal slug) — only resolves domains that are `status: active` AND `domainStatus: verified`.
- **Frontend**: `App.tsx` now checks `window.location.hostname` before normal routing. A hostname not in `VITE_APP_HOSTNAMES` triggers a live `useGetPartnerByDomain` lookup and renders `PartnerSite` directly at `/` (no `/p/:slug` needed) — an unmatched domain shows the same `NotFound` page, never the main Songtai Partners homepage.
- The existing generic `PATCH /partners/:id` handler already spreads whatever fields are in the request body, so `customDomain`/`domainStatus` are settable through it automatically — no handler change needed there.

## Products & FAQs now sync live from the main database — no more duplication

New `artifacts/api-server/src/lib/mainDatabase.ts` reads directly from the **main** Songtai Life Supabase project (`https://auyjxchghtetxpiyecds.supabase.co`, public anon key — read-only, safe) on every request. `products.ts` and `faq.ts` were rewritten to serve this live data instead of a local copy:

- Whatever an admin edits in the **main** Songtai Life admin panel (product name, price, images, video, active/inactive, FAQ content) now appears here automatically.
- `POST`/`PATCH`/`DELETE` on `/products` and `/faq` in **this** app now return a clear `409` explaining that content is managed from the main admin panel — silently accepting a local edit that would never actually show anywhere would be far more confusing than saying so directly.
- **Two honest simplifications, not bugs**: this app's `Product` type only supports one image and one video URL, while the main catalog supports multiple images and per-language video — the first image and the English video (falling back to French) are used. And there's no `stock`/inventory concept in the main catalog at all, so every synced product is reported as in-stock rather than defaulting to 0 (which would incorrectly show everything as sold out).
- **Not done this pass, flagged rather than faked**: `gallery`, `about`, and `testimonials` were NOT wired to the main database. `testimonials` has no equivalent at all in the main site's database — that data only exists in this app locally. `gallery` and `about` have real main-DB equivalents (`gallery_albums`/`gallery_images`, `page_sections`) but with substantially different shapes (albums vs. flat list; mission as a bullet-point array vs. plain text) — reconciling those needs the same treatment as products/FAQ but wasn't done in this pass given scope.
